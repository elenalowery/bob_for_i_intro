Security and Guardrails in Bob

Protection operates at multiple layers — from the LLM itself all the way to connected external systems

Layers of security

1
Frontier LLM — built-in safety guardrails
  • IBM vets and tests every LLM before it is made available in Bob.
  • LLMs refuse harmful, unethical, or out-of-policy requests by design.
  • Responses are grounded in context — the model does not act outside the conversation.
  • No training on your code or data: conversations are not used to retrain the underlying model.
2
Agentic harness — reasoning and execution controls
  • Bob plans and confirms multi-step actions before executing them — it does not act silently.
  • Tool invocations are visible in the UI; you can review and cancel before they run.
  • Auto-approval mode is off by default — each tool call requires explicit confirmation unless you enable it.
  • Context scope is controlled: Bob only accesses files and systems that are explicitly in scope for the task.
3
Configuration — allowed commands and MCP server settings
  • Allowed commands: administrators can restrict which CL, SQL, and PASE commands Bob is permitted to invoke — preventing destructive or unauthorized operations.
  • MCP servers: each server is explicitly registered in the Bob configuration; Bob cannot reach systems that are not configured.
  • Modes and skills can be scoped to specific roles or projects, limiting what Bob is instructed to do per context.
4
IBM i connection — operating system authority
  • All IBM i operations run under the user profile of the active Code for i (SSH) connection.
  • Bob inherits that user's object-level authority — it cannot exceed what the connected ID is permitted to do.
  • Object-level security, library lists, and adopted authority all apply as normal.

MCP server authorization

  • MCP servers act as the integration point between Bob and external systems (databases, APIs, services).
  • Each MCP server is responsible for enforcing its own authorization — Bob passes requests; the server decides what is allowed.
  • Credentials and secrets for external systems should be stored in the MCP server configuration, never in prompts or code.
  • Use scoped API keys or service accounts with least-privilege access for each MCP server.

What to watch out for

  • Auto-approval: enabling it speeds up workflows but removes the confirmation step — use with caution in production environments.
  • Context leakage: workspace files are included in context by default — exclude sensitive files or folders if they should not be seen by the LLM.
  • Prompt injection: untrusted content in files (e.g. malicious instructions embedded in source code comments) can influence Bob's behavior — be deliberate about what you include in context.
Key principle: Bob operates within the boundaries you define. The tighter the configuration — allowed commands, MCP scopes, user authority, and context scope — the more predictable and secure the behavior.
